# Castelei — guia para o Claude Code

Plataforma de estudos que ensina o conteúdo **e** a linguagem da prova. Cada lição é uma sequência de etapas (uma ideia por tela) seguida de questões em Modo Prova. Dono do projeto: Sávio (estudante de ADS no IFBA). Fale em **português do Brasil**.

O planejamento completo, com o **Guia Editorial de Conteúdo**, está em `docs/planejamento.md`. Leia antes de escrever lições.

## Estrutura

- `backend/`: API Laravel 12 (Sanctum, PostgreSQL em produção, SQLite em dev e testes).
- `frontend/`: Next.js 16 (App Router), React 19, Tailwind 4. É um PWA.
- `scripts/lint-content.mjs`: verificador do Guia Editorial (roda no conteúdo, não no código).
- `docs/`: planejamento, **design system (`design-system.md`)**, guia de deploy (`deploy-vercel.md`), **lançamento na Play Store (`play-store.md`)**, mapa das aulas de Sistemas Operacionais (`sistemas-operacionais-mapa.md`), **painel de conteúdo (`painel-admin.md`)**, **revisão espaçada e a ciência por trás dela (`revisao-espacada.md`)**, **próximos passos combinados (`proximos-passos.md`: gerador de cursos, estatísticas novas, vídeo)**, **plano de conteúdo: o básico de cada área e as trilhas (`plano-de-conteudo.md`)**, **os princípios pedagógicos e onde cada um mora no código (`principios-pedagogicos.md`)**.
- `frontend/src/components/ui/`: os componentes do design system (`Card`, `Callout`, `Pill`, `Stat`, `ProgressBar`, `ListRow`, `EmptyState`). **Leia `docs/design-system.md` antes de mexer em tela.**
- Conteúdo das lições: `backend/database/seeders/content/*.json` (**fonte de verdade**). Figuras SVG: `frontend/public/figuras/`.

## Como rodar e testar

```bash
# API
cd backend && composer install && cp .env.example .env && php artisan key:generate
touch database/database.sqlite && php artisan castelei:setup && php artisan serve   # :8000
php artisan test

# App (outro terminal)
cd frontend && npm install && cp .env.example .env.local && npm run dev             # :3000
npm test && npm run lint && npm run build

# Conteúdo (deve passar sempre que mexer nos JSON)
node scripts/lint-content.mjs
```

Plano de um usuário: `php artisan castelei:plan email@exemplo.com plus`.

## Decisões de arquitetura

- **A vitrine é a única parte que lê o backend sem sessão**, por `GET /api/catalog`. Ela nunca pode cair junto com ele: qualquer falha vira a lista de reserva de `site-content.ts`, e o pedido tem prazo de 2,5 s para não pendurar a página.
- **O navegador nunca fala com a API.** O Next guarda o token do Sanctum em cookie `httpOnly` (`castelei_token`) e repassa só as rotas de prática (`frontend/src/lib/proxy.ts`). `frontend/src/proxy.ts` protege as telas do app.
- **O app exige conta** (decisão do Sávio, outubro de 2026): `GUEST_MODE=false` no projeto `castelei`. Sem sessão, `proxy.ts` manda para `/entrar`; uma sessão de VISITANTE que sobrou do modo de teste é mandada pelo `(app)/layout.tsx` para `/cadastro`, que a transforma em conta sem perder o histórico. O site público continua aberto. O modo de teste continua no código: com `GUEST_MODE=true`, cada navegador volta a ganhar uma conta de visitante.
- **O visitante vira conta sem perder nada** (`POST /api/me/claim`, `AuthController::claim`). Criar conta nova do zero deixaria o histórico preso num visitante que a pessoa nunca mais acessa; então o MESMO usuário ganha nome, e-mail e senha, e o token da sessão segue valendo. Visitante é a CONTA (`is_guest`, e-mail em `@guest.invalid`), não o modo do servidor: o Perfil mostra "Criar minha conta" e "Já tenho conta: entrar" só para ela, e a tela inicial convida quem já estudou algo. `/cadastro` escolhe sozinho entre criar a partir do visitante e cadastrar do zero; `/entrar` funciona também no modo de teste (é o caminho de quem abre o app em outro aparelho), com "Continuar sem conta".
- **Entrar com o Google** (`AuthController::google`, `Support\Auth\GoogleSignIn`, `lib/google.ts`, rotas `/api/auth/google` e `/api/auth/google/callback` do Next). O navegador vai ao Google e volta para uma rota NOSSA; quem troca o código pela identidade é o Laravel, com o segredo do cliente, e confere `aud`, `iss`, `exp` e `email_verified`. O `state` num cookie de 10 minutos prova que quem volta é quem saiu. Quatro casos, nesta ordem: mesmo `google_id` (a mesma conta); mesmo e-mail (a conta ganha o Google, sem duplicar); visitante (vira a conta Google SEM perder o histórico, mesma ideia do `claim`); senão, conta nova. A volta passa por `/entrar/google`, que apaga as páginas guardadas da conta anterior. **Sem chaves, a função não existe:** sem `GOOGLE_CLIENT_ID` no `castelei` o botão some, e sem `GOOGLE_CLIENT_ID`+`GOOGLE_CLIENT_SECRET` no `castelei-api` a rota dá 404. O endereço de volta cadastrado no Google Cloud é `https://castelei.vercel.app/api/auth/google/callback` (e `http://localhost:3000/...` para testar).
- **A tela Planos descreve o corte decidido**: tudo que existe hoje no grátis; o Pro ganha só o simulado e os níveis de dificuldade. O Plus saiu da vitrine. A cobrança continua não implementada.
- **Site público separado do app.** `src/app/(site)/` guarda tudo que abre sem login (`/`, `/como-funciona`, `/materias`, `/privacidade`, `/excluir-conta`), com cabeçalho e rodapé de site. O app continua em `(app)`, com a moldura de aplicativo. O catálogo anunciado no site fica em `lib/site-content.ts` — não vem da API, para a vitrine não cair junto com o backend, e um teste (`site-content.test.ts`) reprova se ele divergir do conteúdo de verdade.
- **Planos:** limite de questões por lição no servidor (Grátis 5, Plus 30, Pro sem limite) em `backend/config/castelei.php`. Pagamento **não** está integrado. **Decisão do Sávio:** quando entrar, vai ser pelo faturamento do próprio Google Play. Dentro de um TWA isso não é a biblioteca de Android, e sim a Digital Goods API + Payment Request, com validação do *purchase token* no servidor — o caminho completo está em `docs/play-store.md`.
- **O CORTE ENTRE GRÁTIS E PAGO JÁ ESTÁ DECIDIDO, e implementado, com os níveis escritos nas matérias públicas.** Decisão do Sávio, tomada com o app inteiro no ar: **tudo que existe hoje fica no plano grátis**, inclusive as oito questões por lição, a trilha, o vocabulário, a revisão espaçada e os lembretes. **Só duas coisas separam o pago:**
  - **O simulado por matéria vira Pro.** Ele já existe (`ExamController`) e hoje passa pelo `hasExam()`.
  - **Níveis de dificuldade nas questões, no Pro** — fácil, média e difícil, com o nível **indicado na tela da questão**. É aí que o número de questões deixa de ser oito e passa a ser bem maior: as oito de hoje continuam sendo o que o grátis recebe, e o Pro ganha o resto por cima. Isso mexe no conteúdo (um campo de nível por questão, e questões novas em cada nível), na régua do `lint-content.mjs` (que hoje espera oito) e na vitrine (que já sabe parar de prometer um número fixo).

  **O corte já está no código** (`config/castelei.php` → `plans`): grátis com 8 questões por lição e gamificação, Pro com o simulado e os níveis (`Plans::hasLevels`). **As matérias públicas de questão já têm os níveis**: Português, Matemática Básica e Lógica, com seis por lição (duas fáceis, duas médias e duas difíceis, com os distratores nos quatro moldes do Guia). Produção Textual fica de fora, porque a prática dela é escrita. Matéria nova pública entra já com os níveis. **A prática comum é só das questões de BASE** (sem nível), para todo mundo; as com nível ficam em "Praticar por nível" (`AttemptController::store`). Misturadas, o Pro treinaria 14 questões de dificuldade sorteada, e o domínio do Progresso (que conta a base) deixaria de bater. Lição em que todas têm nível segue o corte antigo. A vitrine promete "8 por lição" contando só a base, e o verificador reprova questão com nível antes de uma de base. Cada questão tem `difficulty` opcional (`facil`, `media`, `dificil`; nulo = sem nível), que entra pelo JSON, pelo painel e pelo export, e o verificador reprova valor fora da lista. A prática comum continua igual (o grátis recebe as oito primeiras pela posição, por isso questão com nível entra DEPOIS delas). `POST /lessons/{id}/attempts` aceita `level`: vem todo o nível, sem corte, e quem não é Pro recebe 403. A última etapa da lição mostra "Praticar por nível" (`LevelPicker`) só com os níveis que existem, trancados para o grátis com o link para os planos, e a questão mostra a etiqueta do nível ao lado do tópico. O `UNLOCK_ALL` continua dando Pro a todo mundo enquanto for fase de testes, **menos** as contas listadas em `REAL_PLAN_EMAILS` (e-mails por vírgula, no `backend`): elas enxergam o plano de verdade, para o Sávio ter uma conta grátis e ver o que fica faltando. Os testes que exercitam o mecanismo do corte usam um grátis menor (5, sem gamificação) no próprio `setUp`; o corte decidido é conferido em `PlansTest`.
- **FASE DE TESTES — tudo liberado.** `UNLOCK_ALL` (padrão **ligado**) faz todo mundo estudar como Pro. Passa por `Plans::effective()`; o plano guardado em cada usuário não muda, então trocar o padrão para `false` devolve os limites sem migração. É a chave a desligar no lançamento.
- **Identidade visual é própria, e isso é decisão.** Nenhuma biblioteca de design de terceiros entra como base — Carbon traz a cara da IBM, Primer a do GitHub, e o padrão do shadcn/ui virou a cara dos apps de IA. O Atlassian Design System foi avaliado e descartado por licença (só vale para produtos integrados à Atlassian, e proíbe obras derivadas). Comportamento complexo, quando precisar, vem do Radix UI (MIT), sem visual junto.
- **Gamificação** (XP 20 por acerto, streak em dias no fuso `America/Sao_Paulo`, 10 conquistas): dados guardados para todos; só Plus/Pro veem. `GAMIFICATION_FOR_ALL=true` (backend) libera para todos, e está ligado no Railway para testes. Falhas da gamificação nunca podem quebrar o estudo (tudo em `try/catch`).
- **Etapas de lição** (`lessons.steps`, JSON): `kind` (`idea` primeira, `recap` última, uma `exam`, uma `pitfall`), `title`, `body`, e opcionais `example`, `bullets`, `terms`, `figure`, `video`, `code`, `table`. Formato completo no `README.md`. Colunas antigas (`explanation`, `exam_style`, `pitfalls`) são derivadas das etapas pelo `ContentSeeder`.
- Lições são identificadas por `(matéria, slug)` e questões por `(lição, posição)`: **não reordene questões já publicadas**. Por isso o painel não deixa editar slug depois de criado.
- **A lição guarda o nome do módulo, nunca o número** (`lessons.module`, opcional). A tela da matéria agrupa lições **seguidas** com o mesmo nome e numera pela ordem. Se o número morasse no conteúdo, reordenar a matéria deixaria um "Módulo 5" antes do 4. Nome vazio vira nulo: matéria sem módulos vira uma trilha só.
- **Só existe um caminho de escrita em massa de conteúdo:** `App\Support\Content\ContentImporter`. O `ContentSeeder` do deploy e o painel usam o mesmo código, inclusive para derivar as colunas antigas. Dois caminhos para a mesma tabela viram duas regras diferentes na primeira correção feita em um só.
- **Matéria e trilha podem ser PRIVADAS** (`subjects.visibility`, `"visibility": "private"` no arquivo, "Quem vê" no painel; trilha com `visibility` em `config/castelei.php`). Decisão do Sávio para o lançamento: o público recebe **o básico de cada área** (hoje Matemática Básica, Português, Lógica e Produção Textual, com a trilha "Base para provas"), e o que nasceu para ele (Sistemas Operacionais, Servidores, Refatoração, Python, a trilha de LLMs com as suas seis matérias, Montar um PC) fica privado. Privada só aparece para quem **administra** (`Subject::scopeVisibleTo`, `isAdmin`): é o rascunho que se estuda antes de abrir. Quatro coisas:
  - **Uma tranca só, o middleware `visible`**, em toda rota que recebe `{lesson}` ou `{subject}` fora do painel. Responde 404, não 403 (403 confirmaria que existe). Rota nova com lição ou matéria precisa dele.
  - **A vitrine (`/api/catalog`) só anuncia a pública, sempre** — ela não tem sessão. `site-content.ts` também não lista privada, e o teste dele filtra os arquivos pela visibilidade. A questão de exemplo da home passou a ser de Lógica.
  - **A migração marca as privadas pelo slug**, além do arquivo: matéria que passou para o painel o seeder pula, e ela ficaria aberta.
  - **O histórico continua, as estatísticas não apontam para lá.** `/progress/stats` filtra as matérias que a pessoa não vê, porque o mapa e as listas são links.
  O que vem depois (básico de cada área, trilhas ENEM, a ordem de escrita) está em `docs/plano-de-conteudo.md`.
- **Toda matéria guarda de onde vem** (`subjects.origin`): `seed` = os arquivos de `database/seeders/content/` ainda mandam; `painel` = foi editada em `/admin` e o `ContentSeeder` pula ela. A troca acontece na primeira escrita do painel, inclusive numa lição ou questão dela. Sem isso, o pre-deploy do Railway recarregaria o arquivo antigo por cima de toda edição — sem erro e sem aviso. O teste que trava isso é `ContentImportTest::test_o_seeder_nao_desfaz_o_que_o_painel_editou`.

## Painel de conteúdo (`/admin`)

Publicar matéria sem mexer em código nem esperar deploy. O guia completo está em `docs/painel-admin.md`; o essencial:

- **A mesma conta do app**, com uma permissão a mais. `ADMIN_EMAILS` (lista por vírgula) é a porta de entrada — no Railway dá para criar variável pelo navegador, mas rodar comando exige CLI. Depois disso, `php artisan castelei:admin email` (`--remover` tira). Plano Pro **não** dá acesso: plano é sobre estudar, permissão é sobre publicar. Conta de visitante do `GUEST_MODE` nunca entra.
- **Três camadas de barreira, e a que conta é a de baixo:** o middleware `admin` na API é a tranca; o proxy do Next (`/api/admin/[...path]`) é só encanamento, que põe o token do cookie `httpOnly` no header; a guarda em `(painel)/layout.tsx` é conforto, para a pessoa ler uma explicação em vez de um 403 numa tela branca.
- **Duas réguas diferentes, de propósito.** `App\Support\Content\ContentValidator` separa **erro** (quebra o app: campo faltando, `correct_index` fora da lista, slug repetido, figura sem `alt` útil) de **aviso** (Guia Editorial: falta `idea`/`recap`, número de alternativas ≠ 5, de questões ≠ 8). O verificador completo continua sendo `scripts/lint-content.mjs`, que roda na máquina de quem escreve — o painel existe justamente para publicar sem esse ambiente montado.
- **O importador nunca apaga sozinho.** Arquivo que encolheu gera `orphan_lessons`/`orphan_questions` no relatório; só some com `prune` ligado, e a tela diz o que vai junto (respostas e tentativas de quem já estudou).
- **A matéria sai por onde entrou.** `GET /api/admin/subjects/{id}/export` (botão "Baixar esta matéria" na tela da matéria) devolve o arquivo de importação completo, e o que sai **entra de volta sem perda** — um teste compara exportar→reimportar→exportar. Sem isso, matéria escrita no painel ficava presa no banco: sem versionamento, sem passar pelo `lint-content.mjs` e sem ninguém poder revisar num editor. Cuidado com o `correct_index`: a alternativa A é 0, e um `array_filter` ingênuo apagaria o gabarito.
- **O editor de etapas é de blocos, não de JSON** (`StepsEditor`, `StepCard`, `BlockFields`, lógica pura em `lib/steps.ts`). O campo de JSON cru que havia aqui apostava que o fluxo seria sempre "a IA gera, o painel confere e publica". A aposta quebrou na primeira vez que alguém escreveu um curso à mão: pôr uma figura exigia escrever JSON, escrever mais um parágrafo não exigia nada, e saiu um curso inteiro de texto corrido. **A ferramenta ensinou isso.** Quatro decisões:
  - **Os botões de bloco ficam sempre à vista**, com a frase do que cada um serve. Escondidos num menu é o que faz esquecer que existem.
  - **O medidor de paredão** mostra, enquanto se escreve, a mesma conta que o validador faz depois de salvar. Aviso que chega junto com o "salvo" raramente faz alguém voltar.
  - **Lição nova já nasce com uma figura e uma tabela em branco.** Campo vazio à vista puxa para ser preenchido; bloco que precisa ser acrescentado é bloco que se esquece. `limpar()` descarta o que ficou vazio antes de salvar.
  - **O modo JSON continua ali** para quem chega com conteúdo pronto. Enquanto o JSON está pela metade vale a última versão boa — devolver a cada tecla esvaziaria a lição.
- **Aviso de "lição só de texto corrido"** (`ContentValidator::tooMuchProse` e `checkVisuals` no lint). Nasceu de um caso real: um curso inteiro escrito pelo painel saiu sem uma figura, tabela ou exemplo em lição nenhuma — o conteúdo certo, a tela um paredão. Conta `figure`, `video`, `table`, `code`, `example`, `bullets` e `terms`; o piso é um terço das etapas. É **aviso**, nunca erro: forma não reprova conteúdo.
- **Modelo comentado** em `backend/resources/content/modelo-conteudo.json`. Chaves começadas por `_` são comentário e saem na importação (`ContentImporter::stripComments`). Um teste garante que o modelo passa na própria conferência sem erro nem aviso — se mudar o validador, o modelo tem que acompanhar.
- **Mídia:** `/admin/midia` guarda imagem e vídeo no disco de `castelei.media.disk` e devolve o endereço para colar na etapa. No Vercel o disco é o próprio banco (`MEDIA_DISK=database`), porque a função não tem disco que dure. Trocar para externo é `MEDIA_DISK=s3`; nada no código muda.
- **A entrega da mídia é a rota `GET /api/media/{caminho}`, não o `public/storage` do Laravel.** O atalho é criado por `storage:link`, que só rodaria no pre-deploy do Railway — contêiner separado e descartável, montado antes do volume. O atalho nunca chega ao contêiner que atende as requisições: o log diria "link has been connected" e toda imagem responderia 404. **Não devolva o `storage:link` ao `castelei:setup`.**
- **A vitrine se anuncia sozinha.** `/materias`, `/` e `/como-funciona` leem `GET /api/catalog` (rota pública, só nome de matéria e título de lição) por `frontend/src/lib/site-catalog.ts`, com cache de 1 minuto. Matéria criada no painel aparece sem deploy. `site-content.ts` virou **rede de segurança**: vai ao ar quando a API falha, demora mais de 2,5 s ou responde fora do formato — por isso `site-content.test.ts` continua exigindo que ela fique igual aos arquivos. O `pitch` não existe no banco (é texto de venda): matéria nova se anuncia com a `description`. E "8 questões por lição" deixou de ser fixo: a rota devolve nulo quando o número varia, e a vitrine para de prometer em vez de mentir.

## Regras de conteúdo (do Sávio, valem sempre)

1. **O app é independente.** Nunca cite livro, autor, capítulo ou página dentro das lições. O livro-base da disciplina só serve para estruturar os assuntos; pode e deve usar conhecimento de qualquer boa fonte. O verificador reprova referências a fontes.
2. **Escreva para quem parte do zero.** Explique mais, em mais etapas, com exemplos do dia a dia. Se um iniciante trava, o texto está errado.
3. **Comandos sempre dizem onde funcionam:** Windows (PowerShell e cmd), Linux, ou os dois. Quando houver dois jeitos, mostre os dois (use o bloco `table`). Explique como abrir e usar o shell.
4. **Informação atualizada:** se algo da fonte estiver defasado, corrija com conhecimento atual (confira na internet).
5. Guia Editorial: analogia antes de definição, concreto antes de abstrato, nunca use um termo sem explicá-lo antes (na própria lição), sem "como vimos anteriormente", frases curtas (mais de 2 vírgulas, quebre), jargão de banca só na etapa "Como cai na prova".
6. Toda figura precisa de `alt` descritivo e legenda. Figuras são **originais** (não copie figuras de livros).
7. **O slide da aula é base, não teto.** A cada aula o Sávio manda o slide do professor. O trabalho é comparar com a lição correspondente, acrescentar o que faltar e **aprofundar** — inclusive o que o slide explica mal, que é a maior parte do valor. Duas balizas:
   - **Profundidade não é complicação.** Aprofundar é dizer por que a coisa é assim, mostrar o mecanismo e dar o exemplo concreto; não é encher de termo novo nem escrever mais denso. Se a etapa ficou mais difícil de ler, foi para o lado errado.
   - **O slide não manda no recorte.** Ele diz o que o professor vai cobrar, e isso entra. Mas a ordem, a analogia e a divisão em etapas continuam sendo as do Guia Editorial — não copie a estrutura do slide, e nunca copie a figura dele.
8. **Matéria pública fala com qualquer pessoa.** Exemplo do dia a dia de quem estuda para uma prova, nunca do curso, do trabalho ou do interesse de quem escreveu. Matéria básica não aponta para matéria avançada que a pessoa não escolheu.
9. **Toda alternativa errada é um erro de verdade**, num dos quatro moldes do Guia Editorial (palavra trocada, quantificador absoluto, parte pelo todo, inversão). Nos níveis de dificuldade, “difícil” é o distrator mais fino, não a conta mais longa.

## Deploy (Vercel + Neon)

Dois projetos no Vercel ligados a este repositório: `castelei` (Root Directory `frontend`) e `castelei-api` (`backend`), mais o Postgres no **Neon**, criado pela aba Storage do Vercel. **Cada push na `main` publica os dois.** O passo a passo, com as variáveis, está em `docs/deploy-vercel.md`. Saímos do Railway em outubro de 2026 (o teste acabou), e o banco **começou do zero** por decisão do Sávio: as matérias do repositório voltam sozinhas, e contas, progresso, mídia enviada e a matéria Projeto Number Race (que só existia no painel) ficaram para trás.

- **A API é PHP rodando como função**, pelo adaptador da comunidade `vercel-php` (`backend/vercel.json`, entrada em `backend/api/index.php`). A função só escreve em `/tmp` e o que fica lá some: por isso os caches do Laravel apontam para `/tmp`, sessão é `array`, cache é o banco e log é `stderr`. As variáveis que não são segredo moram no `vercel.json`.
- **As migrações rodam no BUILD, só em produção.** O script `vercel` do `composer.json` (o adaptador o executa ao montar a função) chama `castelei:setup` quando `VERCEL_ENV=production`. Deploy de outra branch não toca o banco. Setup que falha derruba o build, e a versão anterior segue no ar — o mesmo papel do pre-deploy de antes.
- **A mídia mora no banco** (`MEDIA_DISK=database`, tabela `media_files`, `Support\Media\DatabaseAdapter`, em base64 porque o `bytea` volta diferente no Postgres e no SQLite). O Vercel limita o envio a 4,5 MB, então imagem e vídeo do painel ficam em 4 MB; vídeo maior vai pelo YouTube.
- **`DATABASE_URL`** é o nome que a integração do Neon cria; o `config/database.php` usa ele quando `DB_URL` não existe.
- **O endereço público do site** sai de `SITE_URL` ou, sem ela, de `VERCEL_PROJECT_PRODUCTION_URL` (`lib/site-url.ts`).
- Segredos ficam nas variáveis do projeto `castelei-api`: `APP_KEY`, `ANTHROPIC_API_KEY`, `VAPID_PUBLIC_KEY`/`VAPID_PRIVATE_KEY`/`VAPID_SUBJECT`, `CRON_SECRET` (o mesmo valor do secret `CASTELEI_CRON_SECRET` do GitHub), `ADMIN_EMAILS` e `REAL_PLAN_EMAILS`. No `castelei`: `API_URL` (terminando em `/api`), `GUEST_MODE=false` e `GOOGLE_CLIENT_ID`.

**Existem três formatos de questão** (`questions.format`). O primeiro é o de sempre: cinco alternativas, uma certa — e continua sendo o principal, porque é o formato da prova que o aluno vai fazer. O segundo é **pôr os passos na ordem** (`order`), e ele existe porque a múltipla escolha só mede RECONHECER. Boa parte da matéria não é sobre reconhecer: `fork` vem antes de `execve`, o pedido vem antes do TRAP, liberar o SSH vem antes de ligar o firewall. Quem troca a ordem quebra a máquina, e a alternativa nunca cobra isso. Cinco coisas:

- **O gabarito é a PRÓPRIA lista de opções**, escrita na ordem certa. Não existe `correct_index` — ele fica em zero só porque a coluna não aceita nulo, e ninguém o lê.
- **Por isso o servidor embaralha antes de entregar** (`Support\Practice\StepShuffle`). Mandar a lista como está entregaria a resposta a quem abrisse as ferramentas do desenvolvedor — o mesmo cuidado que a múltipla escolha já toma com o `correct_index`. A semente é `tentativa + questão`, então a ordem é reproduzível nas duas pontas **sem guardar nada**, e duas pessoas na mesma questão veem ordens diferentes. Um teste garante que o sorteio nunca cai na ordem certa.
- **Não se arrasta, se toca.** Arrastar dentro de uma página que rola é o gesto que mais erra no celular: o dedo ora arrasta o item, ora rola a tela. Tocar sobe o passo para "sua ordem"; tocar de novo o devolve **ao lugar de onde saiu**, não para o fim da fila.
- **Confirmar só acende com tudo posicionado** — até lá o botão conta quantos faltam. Ordem pela metade não é resposta errada, é resposta incompleta, e mandá-la gastaria a questão.
- **Errar mostra a ordem certa com um certo em cada passo que ficou no lugar.** Só "errou" não ensina nada aqui: o que falta saber é ONDE a sequência saiu do trilho.

Ao escrever conteúdo: use `order` onde a lição ensina uma sequência, e múltipla escolha no resto. De três a seis passos (menos de três, metade acerta no chute; mais de seis, vira paciência e não cabe na tela). O verificador reprova `correct_index` numa questão de ordenar, e o painel oferece os dois formatos lado a lado.

**O terceiro formato é ligar os pares** (`match`, com a coluna `questions.pairs`). Ele existe porque duas colunas que se correspondem já estão espalhadas pelo conteúdo: `open` com "abrir um arquivo", `ls` com `Get-ChildItem`, cada termo com o seu significado. Em alternativa isso vira um par por vez; aqui a pessoa precisa saber os quatro ao mesmo tempo, porque usar um par errado tira a opção certa de outro. Quatro coisas:

- **Os pares são DUPLAS (`{left, right}`), e não duas listas paralelas.** Listas alinhadas por posição desalinham na primeira edição feita numa só, e o gabarito troca sem que nada reclame. `options` fica vazia nesse formato, de propósito.
- **A coluna da direita vai embaralhada**, pelo mesmo `StepShuffle` da questão de ordenar. A esquerda vai na ordem escrita — é a direita que a pessoa escolhe.
- **A resposta é a mesma conta das duas.** Ordenar e associar mandam uma permutação do que está na tela: na de ordenar a posição i quer dizer "o i-ésimo passo"; na de associar, "o par do i-ésimo item da esquerda". Por isso o campo na API é o mesmo (`ordering`), e a verificação também.
- **Errar mostra o par certo em texto normal, e o erro embaixo.** A primeira versão punha um X vermelho ao lado da resposta CERTA, e lia-se como "esta é a errada" — justo a linha que existe para ensinar. Medido olhando a tela, não deduzido.

**As alternativas da múltipla escolha também vão embaralhadas** (`StepShuffle`, a mesma conta da questão de ordenar). Quem escreve costuma pôr a certa primeiro: em Sistemas Operacionais ela era a letra A em 200 de 256 questões, e em Servidores em todas — dava para acertar sem saber. Embaralhar no servidor corrigiu as cinco matérias de uma vez, inclusive o que for escrito no painel, sem tocar em conteúdo. Três coisas:

- **A API recebe a posição NA TELA e grava a do conteúdo** (`answers.selected_index`). Assim a resposta gravada continua certa mesmo se a ordem da tela mudar um dia.
- **O `correct_index` da resposta volta na posição da tela**, que é a que o `PracticeClient` destaca. Nos testes, `$this->naTela($tentativa, $questao, $indiceDoConteudo)` (em `tests/TestCase.php`) faz a tradução.
- **O arquivo de conteúdo continua dizendo a posição do conteúdo.** Ninguém precisa mudar nada ao escrever questão: a certa pode ficar onde estiver.

**O bloco `example` tem duas formas** (`StepExample`). **Código na lição vem com tradução linha a linha** (`StepCode`, bloco `code.notes`). Queixa do Sávio estudando chamadas de sistema: "as linhas de código, você parte do pressuposto que eu já entendo de código". Estava certo, e o furo era do verificador — `code.text` não passava por conferência nenhuma, então `waitpid(pid, ...)` podia entrar na tela sem uma palavra de explicação. Rodada a régua nova contra as duas matérias, deram **205 erros**. Cinco decisões:

- **Uma nota por linha de código**, obrigatória (erro no `lint-content.mjs`, aviso no painel). Linha em branco não conta: é respiro, não instrução.
- **A explicação NÃO é comentário dentro do código.** Comentário sai em fonte de máquina, foge junto com a linha na rolagem lateral e não passa pela conferência. Fora do bloco, é texto como qualquer outro — e por isso entra no limite de vírgulas, no de palavras e na conferência de jargão.
- **A numeração é uma coluna ao lado**, não um número dentro de cada linha. Partir o código em um elemento por linha tiraria as quebras de linha do texto, e quem copiasse o bloco levaria tudo grudado. O alinhamento se sustenta porque a linha não quebra (`whitespace-pre` com rolagem lateral).
- **O código entrou no escopo `s` do verificador**, junto com os nomes que ele usa: `fork`, `execve`, `waitpid`, `open`, `read`, `write`, `O_RDONLY`, e também `função`, `variável`, `laço`, `bit` e `byte`. O corte é "quem nunca programou saberia?".
- **Cuidado: o nome do verbete tem que casar com a mesma expressão que reconhece a chamada.** `["down e up", /\bdown\(/]` nunca era marcado como explicado, porque a palavra "down e up" não tem parêntese — o erro não saía nunca, por mais `terms` que se escrevesse.

**A figura mora numa folha branca, e isso não é enfeite** (token `sheet`, em `globals.css`). Os SVG do app são desenhados a tinta escura sobre papel. Colados direto no cartão, no escuro só sobrevivia o que tinha preenchimento claro: as caixas coloridas apareciam, e a borda delas, as setas e todo texto solto sumiam. Não quebrava nada e não avisava nada — as 35 figuras estavam assim desde sempre, e apareceu olhando a lição de hardware no escuro. `sheet` é branco nos dois temas, como `on-accent`: a imagem vira página impressa colada na tela, e a legenda fica no cartão, onde o texto acompanha o tema. Um teste trava o `bg-sheet`. Se um dia as figuras forem redesenhadas para os dois modos, o caminho é `currentColor` no SVG, não mexer na folha.

**Desenho em fonte de máquina não é código.** O endereço partido em dois da lição de memória virtual era um quadro de `+---+` dentro do bloco preto. Virou figura (`so-endereco-partido.svg`). O par `(bloco, posição)` da segmentação virou bloco `example`, que já era português.

**A explicação vem até a pessoa, não o contrário.** Depois de responder, o bloco de feedback rola para o MEIO da tela (`block: "center"`). Era `"nearest"`, que rola o mínimo possível — e o mínimo deixava a explicação encostada na barra fixa de baixo, com a pegadinha cortada. Quem acabou de responder quer ler o porquê, e estava tendo que rolar para isso.

Conta a ÚLTIMA resposta de cada questão, em tentativa concluída: quem errou em setembro e acertou ontem já aprendeu, e refazer essa seria castigo. O resultado oferece o botão com o número (`wrong_count`, que já desconta o que se acertou agora) e a última etapa da lição também; a escrita fica de fora, porque parte de texto não tem "errada". Sem erradas, a API responde 422 — e a tela nem mostra o botão.

**Ferramentas de estudo fora da prática** (`StudyToolsController`, `components/study/`):

- **Anotação por lição** (`lesson_notes`, uma por pessoa por lição, `GET/PUT /lessons/{id}/note`). Mora na etapa de resumo, depois de ler e antes de praticar, e guarda sozinha um segundo depois de a pessoa parar de digitar — botão "Salvar" se esquece. Vai para a conta, não para o aparelho: é histórico de estudo. Texto vazio APAGA a anotação. **Dá para falar em vez de digitar** (`study/useDictation.ts`): quem transcreve é o navegador (Web Speech API), então não custa nada e nenhum áudio passa pelo servidor. Texto e não áudio gravado, de propósito: a busca acha, e ler a revisão leva segundos. Uma fala por toque, porque o modo contínuo do Chrome no Android repete a frase em pedaços. Navegador sem suporte não mostra o botão. **E dá para pedir correção à IA** ("Corrigir minha explicação", `StudyToolsController::reviewNote`, `Support/Notes`): ela compara a anotação com o conteúdo da PRÓPRIA lição (`LessonText`, sem o código) e devolve o que acertou, o que corrigir e o que faltou. Ligada pelo Sávio com Sonnet 5.5 (`NOTE_AI_MODEL`), 5 por pessoa por dia (`NOTE_AI_DAILY_LIMIT`), falha devolve a tentativa. **A `ANTHROPIC_API_KEY` é dividida com a Produção Textual, e cada uma tem seu interruptor:** `NOTE_AI_ENABLED` (padrão ligado) e `WRITING_AI_ENABLED` (padrão DESLIGADO). Antes a chave sozinha ligava a escrita — pôr a chave para a anotação teria ligado as duas sem ninguém pedir. **Toda correção fica guardada** (`note_reviews`, com o texto que foi corrigido): a última volta junto da anotação, e `/correcoes` (link no Perfil e embaixo da correção) lista todas. Rever não pode custar outra correção — era o que fazia a pessoa pedir de novo só para relembrar. **Tirar dúvida vem antes de explicar** (`LessonStudyBox`, abas "Tirar uma dúvida" e "Explicar com minhas palavras"; `askDoubt`, `ClaudeDoubtAnswerer`, tabela `lesson_doubts`). No uso real o Sávio quase nunca tinha o que explicar no fim da lição, tinha o que perguntar. A IA responde com a lição inteira junto e marca "Indo além da lição:" quando sai dela. Limite próprio (`NOTE_AI_DOUBT_DAILY_LIMIT`, padrão 10), mesma chave e mesmo modelo; sem IA a caixa vira só a anotação. As dúvidas também ficam guardadas e aparecem em `/correcoes`.

Sem acento, sem índice: são dezenas de lições, e um motor de busca seria mais um serviço para cair. É formulário GET de verdade — funciona sem JavaScript e o "voltar" devolve aos resultados. A entrada é uma linha no Perfil (grupo Estudo): a lupa saiu do topo, porque lupa no cabeçalho é cara de site.
- **Cartões do vocabulário** (`/materia/[slug]/vocabulario/cartoes`, `lib/flashcards.ts`). Entram as palavras de lições já praticadas (com menos de cinco, a matéria inteira), no máximo vinte por rodada. A pessoa tenta lembrar, vira e diz se lembrou; nada vai para a nota. **A espera antes da primeira questão é um esqueleto** (`PracticeSkeleton`, em `PracticeClient.tsx`), com a forma do cabeçalho, do enunciado e das alternativas. Era uma frase solta no branco, no instante de maior desistência da prática.

O app oferece, não esconde — mudar a lição sozinho confundiria quem volta para revisar.

**O Perfil é uma lista de ajustes, e o Resumo do Progresso agrupa por lição** (`components/ui/Settings.tsx`, `lib/progress-groups.ts`). Queixa do Sávio: o Perfil estava "muito bagunçado" — seis seções de título grande e igual peso. Virou grupos (Aparência e som, Estudo, Conta) com uma linha por ajuste, e o som virou interruptor. No Progresso, um cartão por tópico dava 10 mil pixels de rolagem com oito lições feitas; agora é um cartão por lição, com os tópicos recolhidos. A API passou a mandar `lesson_id` e `subject_name` em cada tópico para isso. A Revisão vazia ganhou o mesmo cabeçalho da cheia, e a próxima revisão marcada virou a notícia da tela.

**O Progresso não mistura texto com questão.** Uma parte escrita leva minutos e não tem certo nem errado: somada ao resto, puxava o tempo médio e fazia o gráfico dizer "você está mais rápido" a quem só tinha trocado de matéria. Os números gerais e os dois gráficos de Evolução contam só questões; os tópicos de escrita continuam no Resumo, com "cumpridas" e "partes" no lugar de "certas" e "tópicos" (`writing` em cada tópico da API).

**O Resumo do Progresso é para BATER O OLHO** (redesenho de outubro de 2026, pedido do Sávio: "tem muito texto, a pessoa quer ver se está bem ou mal, se evoluiu ou não"). Em cima, o acerto num anel animado (`AccuracyRing`) com o veredito em palavras (`comoEstou`) e a tendência da semana (`week.change`: últimos 7 dias contra os 7 anteriores, só com 5 respostas em cada); depois três números, o gráfico "Esta semana" (`WeekBars`, questões por dia), uma barra por matéria (o mapa de quadrados abre num toque) e as lições mais fracas em cartões de refazer. Toda explicação foi para trás de um "?"; retenção e a lista de todas as lições ficam num bloco recolhido. O que vem abaixo continua valendo para as contas.

**As contas do Resumo respondem "o que eu estudo agora?"** (`GET /progress/stats`, `StatsController`, contas da tela em `lib/stats.ts`, peças em `components/stats/`). Queixa do Sávio: a aba era fraca, com números que não ajudavam a decidir nada. Virou quatro perguntas, nesta ordem, e os números gerais (com o tempo por questão) foram para o fim. Quatro coisas:

- **Tudo sai da ÚLTIMA resposta de cada questão**, não da média das tentativas. A média diz como a pessoa foi; a última resposta diz o que ela sabe hoje. Quem refaz as erradas e acerta passa a dominar a lição — a média nunca deixaria.
- **Estou pronto para a prova? e o mapa da matéria moram no mesmo cartão.** Lição dominada é 80% das questões de BASE (sem nível, fora do simulado) com a última resposta certa; questão nunca respondida conta como não dominada, senão acertar uma de oito daria 100%. A frase de prontidão é em lições por semana (por dia na última semana), porque é o número que vira decisão. O mapa é um quadrado por lição, em módulos: dominada tem certo (forma, não só cor), a nunca praticada é contorno tracejado.
- **"Onde eu erro" é por LIÇÃO, não por tópico.** No conteúdo o tópico é quase sempre uma questão só (1.760 tópicos, 16 com duas ou mais): por tópico, a lista era "0%, piorando" por UMA questão errada. A tendência compara a última resposta com a primeira das mesmas questões, com 15 pontos de folga; sem questão repetida, a tela diz "praticada uma vez" em vez de inventar seta. O toque leva a refazer só as erradas.
- **"O que estou esquecendo" conta as respostas dadas DEPOIS de um acerto na mesma questão**, contra o acerto de primeira vez. É a medida de memória de verdade, e não se deixa enganar pelo "refazer as erradas" (que só traz o que já estava errado). Escrita fica de fora das duas últimas, como no resto do Progresso.

**Progresso é dividido em abas de rota**: `/progresso` (números gerais e por tópico), `/progresso/evolucao` e `/progresso/conquistas`, com o controle segmentado em `components/ProgressTabs.tsx`. Era tudo numa tela só e ficou embolado. Ao acrescentar uma aba, mexa também no `loading.tsx` da pasta — é ele que impede o cabeçalho de piscar.

> Conceitos de Sistemas Operacionais · Processos · Estados e Transições · **Escalonamento** · Comunicação e Sincronização de Processos · **Semáforos** · Gerência de Memória · Memória Virtual · Segmentação e Paginação · **Gerência de Disco** · Virtualização · **Estudos de Caso**

O que ela decide: o **escalonamento é tópico próprio**, logo depois de Estados e Transições; os **estudos de caso entram na matéria**, no fim; **história dos SOs e revisão de hardware não entram**. Semáforos e Gerência de Disco são itens explícitos, e por isso ganham lição própria. Impasses, Multiprocessadores e Segurança continuam de fora.

Já escritas, além das 5 primeiras: **Estrutura de um SO** (monolítico, camadas, micronúcleo, cliente-servidor, máquinas virtuais e contêineres), **Processos: o modelo** (programa × processo, tabela de processos, PID, criação, hierarquia e término), **Estados e Transições** (executando, pronto e bloqueado, as quatro transições, quem provoca cada uma, zumbi e suspenso) **Escalonamento** (com e sem preempção, objetivos, tipos de processo, regras de lote e interativas, fatia de tempo, prioridade, inanição e envelhecimento) **Threads** em 2 lições (o que compartilham e o que é próprio; escala no usuário × no núcleo, com goroutines e virtual threads como atualização) **Comunicação entre processos** em 5 lições (condição de corrida; exclusão mútua, das tentativas ingênuas a Peterson e à instrução indivisível; semáforos e mutexes; monitores, mensagens e barreira; os três problemas clássicos) **Memória** em 4 lições (base e limite, troca e fragmentação; memória virtual, paginação e TLB; substituição de páginas, com o relógio e o atropelo; segmentação, com o modo plano do x86-64 como atualização) **Arquivos** em 3 lições (arquivos, pastas e os dois tipos de link; contígua, encadeada, FAT, i-node e faixas contínuas; journaling, cópia ao gravar e cache de escrita) **Dispositivos** em 3 lições (camadas de E/S, controlador × driver e DMA; tempo de busca e as regras de ordem do braço, com o SSD mudando o jogo; arranjos de discos, com a insistência de que RAID não é backup), **Virtualização** em 2 lições (os dois tipos de hipervisor, Popek e Goldberg e a ajuda do processador; contêineres, com namespaces e cgroups) e **Estudos de caso** em 2 lições (Linux e Android; Windows).

Não é chato à toa: é exatamente a confusão que a prova cobra. A lição de hardware resolve as duas de uma vez, com um verbete para cada sentido.

**Impasse entrou pela porta dos fundos.** A ementa o deixa de fora, mas ele é inevitável no jantar dos filósofos e na ordem errada de duas trancas. Está explicado onde aparece, sem lição própria.

**Painel de conteúdo no ar** (`/admin`, ver `docs/painel-admin.md`): importação de matéria por arquivo JSON com conferência antes de publicar e relatório do que entrou, edição de matéria, lição e questão, ordenação de lições, exclusão com o nome digitado, e biblioteca de imagem e vídeo. As etapas ganharam o bloco `video`, que aceita arquivo enviado ou link do YouTube (incorporado no domínio sem cookie de rastreio).

**A tela da matéria é uma trilha, não uma lista** (`components/trail/`, lógica em `lib/lesson-trail.ts`). Trinta lições em fileira não mostram onde você está nem quanto falta. Agora são módulos com barra de progresso, e dentro de cada um as lições formam uma onda de nós com três estados: concluída (verde, com certo), atual (azul, anel pulsando, selo "Agora") e ainda não praticada (cinza). Três coisas que valem saber antes de mexer:

- **Concluída é praticada, não aprovada.** Basta uma tentativa terminada; nota não entra. Cobrar acerto aqui transformaria a trilha numa cobrança, e a qualidade da resposta já é medida em `/progresso`.
- **A cinza continua clicável, de propósito.** O app acompanha um semestre com data marcada: quem revisa Memória na véspera da prova não pode esbarrar num cadeado por ter pulado uma lição de setembro. O cinza orienta, não tranca — por isso também não tem cadeado desenhado.
- **O traço passa por trás dos títulos**, e o título é uma plaquinha levantada (`bg-surface-raised` + sombra) por cima dele. Antes ele se disfarçava de fundo, repetindo cor e grão — o que só funcionava com fundo liso. A plaquinha não depende do fundo.
- **O título mora AO LADO do nó, no lado largo** (`TrailLabel`, `labelSide()`). Embaixo do nó, em letra de 12px, cada lição pedia 164px de altura e o texto — que é o que a pessoa lê — era a menor coisa da tela. Ao lado, a linha cabe em 108px, a letra sobe para 15px e a página da matéria encolheu um quarto. Por isso **o nó nunca para no eixo**: a onda anda só pelas faixas de 30–36% e 64–70%, senão o título ficava com metade da tela menos o círculo. A linha INTEIRA é o link, não só o círculo.
- **A próxima lição é o bloco escuro do topo da matéria**, e o simulado e o vocabulário viraram dois atalhos lado a lado. Antes o bloco escuro era do simulado — o atalho mais raro chamava mais atenção que a lição a fazer, que ficava uma tela e meia abaixo.
- **O módulo escolhe a COR, o estado escolhe a FORMA.** Cada módulo recebe sky, sage ou coral em rodízio pela ordem (nunca do conteúdo, e nunca `brick`: vermelho quer dizer erro). Assim cor diz "em que trecho da matéria você está", e quem carrega o estado é o ícone de certo, o anel com "Agora" e o cinza-cavidade. Foi o que resolveu a queixa de que a trilha era "trinta círculos cinza iguais".
- **O nó é uma tecla, não um adesivo** (`.node` + `.node-sky` e irmãs, em `globals.css`). Degrau de sombra sólida embaixo, que some quando o dedo aperta. As cores `*-deep` existem só para isso.
- **Cada módulo fecha num marco** (`TrailMilestone`, uma bandeira), que só acende completo. Não é link de propósito: não há para onde ir, e alvo que responde ao toque sem levar a lugar nenhum frustra.
- **As estrelas não cobram nota.** Terminar já vale uma, sempre (`stars()` devolve 1 até para 40% e para tentativa sem nota); a segunda e a terceira dependem do acerto. O convite é voltar e melhorar, nunca "você não concluiu".
- **O cabeçalho do módulo gruda no topo**, e é trocado pelo do módulo seguinte. É `position: sticky` puro — sem ouvir rolagem, sem medir nada: cada cabeçalho é o primeiro filho da `<section>` do seu módulo e o navegador faz a troca sozinho. Duas coisas de que isso depende e que quebram **em silêncio**: nenhum ancestral pode ter `overflow: hidden` (o app escapa porque o `globals.css` usa `overflow-x: clip`, que não cria caixa de rolagem), e **a folga entre módulos tem que ficar dentro da caixa de conteúdo da seção**. Padding na `<section>` e margem no próprio cabeçalho ficam FORA do retângulo que prende o grudado: com `pb-14` na seção e `mb-6` na faixa, o cabeçalho desgrudava 80px antes do fim do módulo e o topo da tela passava um trecho sem cabeçalho nenhum. Por isso o respiro mora num invólucro dentro da seção — e é um invólucro, não a div do caminho, porque aquela tem altura fixa em pixels e o padding comeria a sobra embaixo do marco. Medido rolando a tela, não deduzido: um teste trava as duas invariantes.
- **A faixa grudada é baixa e chapada.** Baixa porque, grudada, ela come tela o tempo todo — o cartão alto que havia aqui virou duas linhas e uma barra fina. Chapada e sangrando até a borda (`-mx-5 px-5`, com o grão do fundo junto) porque a trilha passa POR BAIXO dela: cartão solto deixaria o traço do caminho aparecer pelos cantos arredondados. O `padding-top` é `env(safe-area-inset-top)`, senão o cabeçalho nasce por baixo do relógio do celular.
- **A faixa de resumo da matéria mostra a PROVA, não XP** (`SubjectSummary`). A tentação era um cabeçalho de XP e streak no estilo dos apps de idioma. Duas razões para não: XP é da conta, não da matéria — é o mesmo número em Português e em Sistemas Operacionais, então não informa nada sobre a tela em que está —, e ele já mora em `/progresso`. O que só ESTA tela sabe é a data da prova, e é o dado que nenhum app de flashcard tem. A contagem informa, não cobra: sem vermelho, sem ícone de alerta e sem mudar de tom na última semana. O progresso da matéria usa o MESMO `concluida()` da trilha de propósito — duas definições de "concluída" é a receita para a barra dizer 6 e o caminho mostrar 7.

**Vocabulário da matéria** (`/materia/[slug]/vocabulario`, motor em `Support\Content\Vocabulary`). A regra 5 do Guia manda explicar todo termo na primeira vez que ele aparece, e a explicação ficava presa ali: quem travasse na palavra três lições depois não tinha onde procurar, e ia para o buscador — que é onde o app perde a pessoa. Quatro coisas:

- **Não existe tabela de glossário, e isso é a decisão.** A lista é montada do bloco `terms` das etapas, que é onde a palavra estreia. Tabela separada seria uma segunda fonte de verdade: envelheceria calada e passaria a discordar da lição.
- **O efeito colateral é o ponto.** Escrever a palavra no `terms` passou a render uma página. Quem escreve ganha motivo para explicar o termo em vez de supor que a pessoa já sabe — o mesmo mecanismo do editor de blocos, que resolveu o curso de texto corrido.
- **Vence a PRIMEIRA aparição**, na ordem de estudo. A palavra volta mais à frente com explicação encurtada, e é a de estreia que foi escrita para quem nunca viu o termo — que é exatamente quem lê o glossário. A ordem é alfabética **sem acento**: senão "Índice" cai depois de "Zona", porque a tabela ASCII põe toda letra acentuada atrás do alfabeto.
- **A tela da matéria só oferece a página quando há palavras** (`vocabulary_terms` em `GET /api/subjects`, que sai de graça porque as lições já vêm com as etapas). Link para página vazia é pior que link nenhum.
- **A palavra de lição ainda não praticada fica APAGADA, nunca escondida** (`seen`, em `GET /subjects/{id}/vocabulario`). A matéria inteira precisa estar na página: quem chega travado numa palavra veio procurá-la, e esconder o que ainda não foi estudado transformaria o glossário numa tranca. Mas a lista completa, na primeira semana, é uma parede de palavras que a pessoa nunca viu, sem como saber o que já é seu. Apagado resolve os dois — continua legível e continua clicável. Mesma decisão do nó cinza da trilha, e o mesmo critério de "praticada" das outras telas: tentativa **concluída**, sem cobrar nota. A contagem "19 já apareceram" e a legenda só aparecem quando há o que dizer: "0 de 166" na primeira visita é cobrança.
- **A letra gruda no topo**, como a lombada de um dicionário, e com a mesma armadilha do cabeçalho de módulo: a folga entre as seções tem que ficar **dentro** da caixa de conteúdo (`pb-8` na lista), nunca entre as seções nem como padding delas. Sem isso eram 16 trechos da rolagem sem letra nenhuma no topo — medido, não deduzido.

**Modo escuro e fundo com profundidade** (tudo em `globals.css` + `lib/theme.ts`). Duas coisas para não desfazer sem querer:

- **A rampa INVERTE no escuro.** `ink` deixa de ser "grafite" e passa a ser "a cor do texto"; `paper`, "a cor do fundo". É o que faz os quase cem `text-ink/70` e `border-ink/15` já espalhados pelas telas continuarem certos sem tocar em nenhuma. O que a inversão não resolve virou papel próprio: `surface-bold` (no escuro ele se destaca por ser mais CLARO que a página), `on-bold` (texto sobre esse bloco) e **`on-accent`** (texto sobre azul, verde ou coral cheios — não muda de tema, porque as cores da marca são claras nos dois; escrito como `text-ink` clareava junto e o botão "Confirmar" ficava ilegível).
- **O fundo é liso de propósito.** Teve brilho de azul-céu e malha de pontos, e o Sávio dispensou. Não era calibragem — foram duas rodadas de força diferente, e o veredito foi sobre o degradê em si. Ficou cor chapada com grão de 3%. Se for mexer, mexa na textura, não em degradê. E lembre que **o topo da página é a barra de status do celular** (`viewport-fit=cover`): cor no alto da página vira barra de status colorida.

**Som ao acertar e ao errar** (`lib/sound.ts`, no Modo Prova). Quatro coisas:

- **Não há arquivo de áudio.** Os dois sons são gerados na hora pela Web Audio: nada a baixar, funciona offline no PWA e o som é nosso, sem licença de banco de efeitos.
- **O erro não grita.** Uma nota grave que desce, e não o "errou!" de auditório. Quem estuda erra o tempo todo — é assim que se aprende. O acerto são duas notas subindo. Volume em 12%, porque isso toca em sala de aula.
- **`primeSound()` é chamada no começo do clique, ANTES do await.** O iPhone só libera áudio dentro de um gesto, e a resposta do servidor chega quando o gesto já passou. Sem isso, o primeiro som de toda sessão é engolido.
- **Interruptor em `/perfil`**, ligado por padrão. Ligar toca o som na hora — é a forma honesta de mostrar o que está sendo ligado, e de quebra libera o áudio no iPhone. Som sem interruptor em app de estudo é motivo para fechar o app.

A escolha do tema (Claro/Escuro/Automático, em `/perfil`) e a do som vivem no `localStorage`, **por aparelho**, e não vão ao servidor. **O padrão é CLARO**, decisão do Sávio ("o claro é mais amigável"): antes era o automático, e todo celular no escuro abria o app escuro sem ninguém pedir. O HTML já sai com `data-theme="light"`; o script no `<head>` (o único embutido do app) só escreve `dark` ou APAGA o atributo no automático, para a tela não piscar antes da hidratação. A cor da barra de status de quem não usa o claro é acertada DEPOIS de hidratar (`ServiceWorkerRegister`): mexida antes, o React recolocava a meta original e a página ficava com duas.

**A revisão espaçada é a primeira parte do app que tem opinião sobre o que estudar** (`lib/review.ts` na tela, motor em `Support/Review/Spacing.php`). Leia `docs/revisao-espacada.md` antes de mexer em qualquer número — eles têm origem medida. O essencial:

- **Com data de prova, não é o algoritmo do Anki, e isso é a decisão.** SM-2 e FSRS resolvem "lembrar para sempre", sem data. Quando a pessoa marcou a prova, para prazo conhecido existe resultado direto: **Cepeda et al. (2008)** mediram, com 1.354 pessoas, que o intervalo ideal é uma **proporção do tempo que falta até o teste** — e que essa proporção CAI quando o prazo cresce: 20 a 40% com uma semana, 5 a 10% com um ano. Usamos 30% a uma semana, 15% a dez semanas e 7,5% a um ano (`ratio_by_horizon`), interpolando em escala logarítmica. Era 15% fixo até outubro de 2026, o que errava as pontas: prova a um ano mandava a lição embora por dois meses.
- **A consequência é o produto inteiro:** o cronograma se comprime sozinho conforme a prova chega. Faltam 90 dias, a lição volta em 13; faltam 30, em 6; faltam 3, amanhã. Nenhum app de flashcard faz isso porque nenhum sabe a data da prova.
- **A crista é larga e assimétrica** (é o que "ridgeline" quer dizer no título do artigo): errar para mais custa bem menos que errar para menos. Por isso o cálculo arredonda para CIMA — e por isso **não precisamos de FSRS**: precisão não compra nada em cima de um platô.
- **A data da prova é de quem estuda, não da matéria** (tabela `exam_dates`, `PUT /subjects/{id}/exam-date`, `ExamDateEditor` na faixa de resumo da matéria). Decisão do Sávio: numa matéria pública, cada um tem a sua prova. O painel não marca mais data; `subjects.exam_date` ficou só como origem da migração (quem já estudava herdou a data).
- **Sem data marcada, quem agenda é o FSRS-4.5** (`Support/Review/Fsrs.php`, parâmetros padrão, estado em `reviews.stability` e `reviews.difficulty`). Sem prazo o problema vira "lembrar para sempre", que é o que ele resolve, e ele aprende com cada lição de cada pessoa. Substituiu a escada fixa de 1, 3, 7, 16 e 30 dias. O estado anda em toda revisão, com ou sem data: apagar a data não recomeça a memória do zero.
- **Os fatores de acerto são calibragem nossa, não estudo** (0,4 abaixo de 50%; 1,3 acima de 90%). Está escrito assim de propósito na documentação: se for afinar alguma coisa, afine isso, não a proporção por horizonte.
- **A revisão abre o Modo Prova, nunca a lição.** Roediger & Karpicke (2006): 61% contra 40% de retenção após uma semana para quem pratica recuperação em vez de reler. O app já fazia certo; faltava o agendamento.
- **Só agenda na PRIMEIRA conclusão da tentativa.** Recarregar a tela de resultado é a mesma prática — reagendar ali daria um dia de folga a cada F5. Um teste trava isso.
- **O atraso não é vermelho.** Vermelho quer dizer erro no Castelei, e estar atrasado numa revisão não é erro: é o motivo de o app existir.
- **Nada é travado**, mesma decisão do nó cinza sem cadeado: a fila sugere, a trilha continua aberta.
- **A revisão é uma ABA da barra de baixo** (Início, Revisar, Progresso, Perfil). Primeiro ela morou na tela inicial como lista, depois como sininho no topo; o Sávio achou estranha uma barra de três abas, e revisar é o hábito de todo dia. A aba mostra o número de vencidas em coral (nunca vermelho), vindo de `GET /me/bar`.

**Lembrete de revisão** (`lib/push.ts` + `PushToggle`, backend em `PushService` e `castelei:lembretes`). O agendamento só vale se a pessoa voltar: um intervalo calculado com 1.354 participantes não serve para nada se o app espera em silêncio. Cinco coisas:

- **Sem chaves VAPID, a função não existe** — e diz que não existe. `GET /api/push/key` responde `enabled: false`, a assinatura responde 503 e o botão some. Mesmo padrão de `/.well-known/assetlinks.json`. Gere com `php artisan castelei:vapid` e ponha `VAPID_PUBLIC_KEY`/`VAPID_PRIVATE_KEY` no serviço `backend`. **Trocar o par depois derruba todas as assinaturas.**
- **Quem dispara é o GitHub Actions, não a hospedagem.** O agendador do Laravel precisa de alguém chamando `schedule:run` a cada minuto, e a API agora é função no Vercel, sem processo de pé. Então `.github/workflows/lembretes.yml` chama `POST /api/cron/lembretes` às 21h UTC, com o segredo em `X-Castelei-Cron` (endereço em `vars.CASTELEI_API_URL`, com `https://castelei-api.vercel.app/api` de reserva). O `Schedule::command` continua em `routes/console.php` porque em qualquer host com cron de verdade ele é o caminho certo — só não é o que roda hoje.
- **Segredo errado na rota de cron devolve 404, não 403.** 403 confirmaria que a rota existe e convidaria a tentar de novo com outro segredo. Sem `CRON_SECRET` configurado, idem: a função não existe. E `hash_equals`, não `===` — comparação que retorna mais rápido no primeiro caractere diferente entrega o segredo letra por letra.
- **O agendamento do GitHub atrasa, e tudo bem.** A crista de Cepeda é um platô largo: chegar uma hora depois não muda a retenção. O que ATRAPALHA é outra coisa — o GitHub **desliga** workflow agendado em repositório sem atividade por 60 dias. Lembrete que parou do nada: olhe isso primeiro.
- **Quem assina é o APARELHO, não a conta.** `push_subscriptions` tem uma linha por navegador, com unicidade pelo resumo do endpoint (ele é longo demais para índice único). A mesma pessoa no celular e no PC tem duas linhas, e desligar num não desliga no outro.
- **`navigator.serviceWorker.ready` nunca rejeita.** Sem service worker ativo ela fica pendurada para sempre — não expira, não dá erro. Por isso existe `registroPronto()`, com prazo: sem ele o Perfil ficava em "Verificando…" eternamente, e foi assim que o problema apareceu (em desenvolvimento o registro nem roda, só em produção).
- **No máximo um por dia, e só com lição vencida.** A crista de Cepeda é assimétrica — chegar um pouco atrasado custa pouco —, então insistir não compra retenção, compra desinstalação. A etiqueta `castelei-revisao` é a mesma todo dia, para o aviso de hoje substituir o de ontem em vez de empilhar. Desligado por padrão: pedir permissão sozinho é o caminho mais curto para um "bloquear" que o app **não consegue** reverter.

**Matéria de Produção Textual** (7 lições em três módulos: artigo de opinião, redação dissertativa — com a proposta de intervenção e as cinco competências — e fábula; `06-producao-textual.json`, figuras em `frontend/public/figuras/producao-textual/`). O Sávio tem dificuldade para escrever e pediu uma matéria em que se aprende escrevendo: a explicação vem em etapas como nas outras, e a prática não são questões — é o texto escrito por partes (tese, introdução, argumentos, conclusão) e, no fim, juntado e revisado. O simulado é o texto inteiro, do zero. Para isso nasceu o **quarto formato de questão, `writing`**, e cinco decisões:

- **Três camadas de correção, da mais barata para a mais cara.** A FORMA (tamanho, frase longa, palavra repetida, marca de fala e o que cada parte pede — `uma_frase`, `conclusivo`, `concessivo`…) é código nosso na tela, em `lib/writing.ts`, enquanto a pessoa digita. A LÍNGUA é o **LanguageTool** (API pública grátis, `Support\Writing\LanguageCheck`): 20 pedidos por minuto POR IP, e o IP é o do nosso servidor, então o limite é de todo mundo junto — se apertar, suba uma instância própria e troque `LANGUAGETOOL_URL`. O SENTIDO é da IA (abaixo). A lista de conferências existe nas duas pontas (`ContentValidator::WRITING_CHECKS` e `WRITING_CHECKS`), e um teste reprova se divergirem.
- **O modelo só aparece depois de escrever.** O roteiro ("tem que ter tal coisa") vai junto da questão; o texto-modelo e a lista de autoavaliação só saem de `POST /attempts/{id}/writing/check`. Modelo mostrado antes vira texto copiado.
- **Conferir não gasta a questão.** Conferir não grava nada e pode ser repetido: escrever, conferir, reescrever é o exercício. Só "Entregar" grava (`answers.text` e `answers.checklist`). A parte conta como **cumprida quando a autoavaliação marca todos os critérios** — é essa conta que vira a porcentagem, o ponto fraco e a revisão, sem mexer em nada do resto do app.
- **A correção por IA está pronta e DESLIGADA, por decisão do Sávio** (medo de gasto acidental). A chave já existe (é da anotação); o que liga esta é `WRITING_AI_ENABLED=true`. Desligada, `POST /writing/review` responde 404 e o botão nem aparece. Com a chave: limite por pessoa por dia (`WRITING_AI_DAILY_LIMIT`, padrão 5), falha devolve a tentativa do dia, e a API é pré-paga (com recarga automática desligada, a conta não cresce sozinha). O modelo é `WRITING_AI_MODEL` (padrão `claude-opus-5`; `claude-sonnet-5` custa menos da metade). Enquanto isso, o botão **"Copiar para corrigir com IA"** monta o pedido com proposta e critérios para colar na IA que a pessoa já usa — custo zero.
- **Lição de escrita não segue a régua das oito questões nem o corte do plano.** São tantas partes quantas o texto tem, e cortar a última entregaria um texto sem a etapa que o junta. As propostas do simulado são questões com `exam_only: true`: moram na lição, mas só o simulado as usa (e a contagem da vitrine as ignora). `draft_only` marca a parte que não entra no texto juntado (a tese sozinha, que já mora dentro da introdução).
- **O rascunho mora no aparelho** (`castelei:rascunho:{questão}`, no `localStorage`) até ser entregue. Texto é trabalho de minutos; perder tudo porque a tela recarregou faz desistir de escrever no celular.
- **Escopo `t` no `lint-content.mjs`** (tese, conectivo, coesão, contra-argumento, concessão, refutação…). O modelo de cada parte passa pela mesma régua de frase das etapas: ele é o exemplo que a pessoa vai imitar. E **os modelos não inventam número** — é regra da própria lição 3, e o texto-modelo não pode desmenti-la.
- **A redação não pede título** (a checagem `titulo` fica só no artigo e na fábula) e **pede `sem_eu_acho` em toda parte**: é texto impessoal. A fábula não tem checagem de conectivo — narrativa não argumenta. As propostas de simulado (`exam_only`) moram na lição que explica os termos que elas usam: a de redação precisa de "tese" e "repertório" definidos, e por isso mora em `redacao-dissertativa`, não na fábula.
- **O painel edita a questão de escrita** num formulário próprio (`WritingQuestionForm`, `QuestionController::validatedWriting`): roteiro e critérios uma linha por item, texto-modelo, tamanho, conferências e as marcas de junção, rascunho e simulado. Ele não troca o formato, e chave de `writing` que ele não conhece é mantida. Criar questão de escrita nova continua sendo pela importação.
- **A tela de lição do painel e a resposta de salvar usam o mesmo `QuestionController::payload`.** A tela montava a lista por conta própria e esquecia o formato: a questão de ordenar ou de associar abria como múltipla escolha, e salvar a convertia sem aviso.

- **Escopo `b` no verificador** (organela, núcleo, DNA, gene, alelo, genótipo, mutação, seleção natural, fotossíntese, bioma, enzima, anticorpo…). "Núcleo" volta a fazer dois trabalhos, como em Sistemas Operacionais: aqui é o da célula, e por isso "eucarionte" não pode ser definido como "célula com núcleo" antes de o núcleo ter verbete.
- **A trilha "ENEM: Natureza" ainda não entra**: o primeiro passo dela é Física, que não existe. Biologia é o último passo.

**Matéria de Lógica** (15 lições, `14-logica.json`, área Matemática, figuras em `frontend/public/figuras/logica/`). Pedido do Sávio: equivalência, negação e tabela-verdade. Cinco módulos: Proposições e conectivos (proposição, negação, “e”/“ou”/ou exclusivo, condicional, bicondicional), Tabela-verdade (montar a tabela e a precedência; tautologia, contradição e contingência), Equivalências e negações (contrapositiva, De Morgan, negação da condicional e da bicondicional, quantificadores), Argumentos (formas válidas, falácias formais, silogismos com diagramas) e Lógica no dia a dia (regras de promoção, filtros de busca, quem descumpre uma regra; era “Lógica no código”, com Python, e mudou quando a matéria ficou pública — o slug `logica-no-codigo` ficou, porque é a identidade da lição). Duas coisas:

- **É raciocínio lógico de prova, e fala a língua dela.** Os mnemônicos que as bancas esperam estão lá (“V com F dá F” na condicional, MANÉ na negação dela), e cada lição tem uma tabela das alternativas erradas que costumam aparecer: recíproca e inversa no lugar da contrapositiva, “nenhum” no lugar de “algum não”.
- **Escopo `q` no verificador**, com o mesmo cuidado de sempre: “verdade”, “conclusão” e “argumento” ficaram de fora por serem palavras do dia a dia; entra “argumento válido”, e a regex pega também “inválido” e “validade”. “Não contradição” casa com “contradição”, então a lição 1 define o princípio pelo nome inteiro.

**Matéria Montar um PC: lendo o nome das peças** (15 lições, `15-montar-pc.json`, área Informática, figuras em `frontend/public/figuras/pc/`). Pedido do Sávio, que vai montar um PC: bater o olho no nome de uma peça e saber se é boa, como já faz com celular. Três módulos de peças (processador, placa de vídeo; memória, armazenamento, placa-mãe e fonte), um de abertura (as peças e o gargalo) e uma lição final que lê um anúncio de verdade linha por linha. Três coisas:

- **A matéria ensina a REGRA do nome, e usa os modelos como exemplo datado.** Hardware envelhece em meses. Toda menção a geração atual vem com o ano (“a série 50, lançada em 2025”), e as próximas gerações aparecem como “esperadas para 2027”, sem nome confirmado. Em outubro de 2026 não havia RTX 60, Core Ultra 400 nem Ryzen 10000 nas lojas. **Ao revisar, confira na internet e atualize os exemplos, não a regra.**
- **Nada de preço.** Preço em real muda toda semana e cada loja cobra uma coisa. Os exemplos de montagem dizem peças e o porquê de cada uma.
- **Escopo `h` no verificador.** “Fonte” entra sozinha, porque aqui é sempre a de alimentação. Cuidado com duas armadilhas que já morderam: “cores” (em inglês, núcleos) casava com “Core Ultra”, e saiu da regex; e “HD” casa com “Full HD”, então a lição escreve “1080p”.

**Narração da lição** (botão "Ouvir", `components/useNarration.ts`, texto em `lib/narration-text.ts`, áudios em `frontend/public/narracao/`). Pedido do Sávio: ouvir ajuda a prestar atenção, mas sem voz robótica. Por enquanto só o **Projeto Number Race** tem áudio, por escolha dele. Quatro coisas:

- **Gravado uma vez, com voz aberta e de graça** (voz Dora, do Kokoro, escolhida pelo Sávio entre cinco abertas; `scripts/narrar.py`). O próximo passo combinado é o Azure (`AZURE_SPEECH_KEY`, plano F0, que recusa em vez de cobrar), regravando os mesmos arquivos. Gerar na hora custaria por uso, e o Sávio já tem medo de gasto que cresce sozinho (ver a correção por IA). Arquivo estático não custa nada para ouvir e funciona sem internet.
- **O nome do arquivo é o resumo do TEXTO narrado**, não o número da etapa. Editar a etapa no painel muda o resumo; o áudio antigo deixa de ser achado, e o botão some até alguém gravar de novo. Áudio lendo um parágrafo que já não está na tela seria pior que áudio nenhum. Por isso o texto tem UMA definição, `narrationText`, que o script de gravação importa direto (`scripts/narracao-textos.mjs`).
- **Código não é lido; a tradução linha a linha é.** Termo em inglês ganha grafia de pronúncia só na hora de gravar (dicionário em `narrar.py`): "Number Race" vira "Nâmber Rêice" na voz, e o resumo continua sendo o do texto da tela.
- **Um elemento de áudio para a lição inteira.** O iPhone só libera som dentro de um toque; o primeiro "Ouvir" libera esse elemento, e trocar o `src` dele quando a etapa acaba continua valendo. Terminou a etapa, a lição avança e a voz segue; na última ela para.

Para gravar outra lição: baixe a resposta de `GET /api/lessons/{id}` (ou use o arquivo da matéria), rode `node scripts/narracao-textos.mjs arquivo.json > textos.json` e `python scripts/narrar.py textos.json`, e commite os `.mp3` com a lista `lib/narracao.json`.

**Trilha de estudo "LLMs do zero"** (`config/castelei.php` → `trails`, `GET /subjects` devolve `trails`, tela em `trilha/[slug]/page.tsx`, lógica em `lib/trails.ts`). Pedido do Sávio: "organize na sequência do que devo aprender primeiro". A trilha atravessa áreas (Matemática e Informática), e a tela de áreas sozinha não dizia a ordem. Quatro coisas:

- **A ordem mora no backend, e o progresso sai das matérias.** Cada passo é só `{subject, name, why}`; praticadas/total vêm das mesmas matérias de `GET /subjects`, com o mesmo critério das outras telas (tentativa concluída).
- **Passo de matéria que ainda não existe aparece como "Em breve"**, com o nome da config, e não é link. Quando o JSON da matéria entrar, o passo acende sozinho. Um teste exige que o `name` do passo seja igual ao da matéria já escrita.
- **Nada é trancado.** O passo atual é o primeiro que existe e não terminou; os outros continuam clicáveis, como o nó cinza da trilha da matéria.
- **A tela inicial mostra a trilha antes das áreas** ("Passo 2 de 8: Programação com Python"), e a matéria que faz parte dela mostra "Passo N de 8 · LLMs do zero" acima do título, com link para a trilha.

## Pendências e cuidados

- **As versões estão travadas nas duas pontas** (`backend/composer.lock` e `frontend/package-lock.json`, os dois versionados). O lock do Composer é resolvido para o PHP mais antigo que roda o projeto (`config.platform.php = 8.3.36`, o do CI), e por isso também instala no PHP 8.5 do `vercel-php` em produção. Atualizar dependência é `composer update` / `npm install pacote@versão` e commitar o lock junto. Antes de subir, `composer audit` e `npm audit` devem dar zero. Em outubro de 2026 saíram correções críticas no PHP (produção já está no 8.5.12, corrigido), no Next.js (fomos de 16.3.5 para 16.4.3, com o sharp 0.35.5) e no Laravel (12.70.2, acima do 12.69 que fecha a falha de login por token).
- **Ilustrações próprias** (`components/illustrations/`): `EmptyArt` desenha as telas vazias (prop `art` do `EmptyState`) e `BadgeMedal` as medalhas. São SVG dentro do React, com as cores por classe do tema (`fill-sky-soft`, `stroke-ink`), para inverter no modo escuro; um `.svg` em `<img>` não enxerga o CSS e precisaria da folha branca das figuras. Mesmo traço em todas (2,5, ponta redonda), fundo sempre na cor `-soft`. Na medalha, a família dá a cor (constância coral, acerto verde, o resto azul), e as de número levam o número escrito. A bloqueada é a mesma medalha apagada, com cadeado.
- **O convite de instalar é guardado na abertura do app** (`lib/install-prompt.ts`, carregado pelo `ServiceWorkerRegister`). O Chrome dispara `beforeinstallprompt` uma vez só, logo que a página carrega; o botão do Perfil escutava só quando o Perfil abria, e o evento já tinha passado — o menu do Chrome oferecia instalar e o nosso botão nunca aparecia.
- **Offline: ler sim, responder não** (`public/sw.js`, `lib/offline.ts`, `components/offline/`). As telas de LER (início, matéria, vocabulário, lição, revisão, progresso — a regex `GUARDAVEL`) são guardadas com rede primeiro: com internet vem a versão de agora, sem internet a última aberta. O botão "Guardar para ler sem internet" na matéria baixa todas as lições de uma vez, e **guarda junto os `/_next/static` que cada HTML cita** — sem eles a lição abria na etapa 1 e o "Continuar" não fazia nada. Responder questão continua exigindo rede, de propósito: o gabarito mora no servidor. As páginas guardadas têm dados da conta, então o cache delas é APAGADO ao sair, ao entrar em outra conta e ao excluir a conta; um teste confere que o nome do cache é o mesmo nas duas pontas. O aviso de "sem internet" aparece no topo do app. Só existe em produção (o service worker não roda no `npm run dev`); para testar, `npm run build && npx next start -p 3001` e `context.setOffline(true)` no Playwright.
